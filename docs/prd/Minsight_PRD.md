# PRD｜Minsight

> 一句话定位：**连接"会议内容生产者"与"下游协作工具消费者"的会议结构化 Agent 中台**——把会议转写文本沉淀为可信、可执行、可追溯的结构化数据资产，自动派生待办与跟进动作，跨会议做去重与冲突检测，并向下游系统（飞书多维表格、任务、日历等）分发，同时对外提供数据概览看板。

| ETL | 抽取（Extract）、转换（Transform）、加载（Load）数据处理流程 |

## 四、需求背景

### 项目背景

会议是企业最高频的协作场景，也是决策与任务的主要发源地，但会议产出高度非结构化：一场会开完，决策散落在对话里、待办口头交代、责任与截止时间模糊。现有工具（详见竞品分析）已能较好完成"转写 + 通用摘要"，但普遍停留在**"可阅读的纪要"**，未能解决三件对企业真正重要的事：

1. **结果不可沉淀**——纪要是一次性文档，无法作为跨会议、可检索、可比对的结构化资产被复用；
2. **结论不可执行**——待办停留在文字，没有真正进入任务系统形成闭环，责任无人跟进；
3. **数据不可信/不可追溯**——负责人张冠李戴、截止时间臆造、决策与讨论混淆，且无证据回链。

本产品据此立项：不做"又一个会议摘要工具"，而做**面向企业的会议结构化 Agent 中台**——以"可沉淀的结构化数据"为核心资产，向上兼容多种会议生产者，向下驱动多种协作消费者，中台自身沉淀数据、派生动作、做跨会议智能比对，并提供数据看板。

作业中同事实现的 V1（单次 LLM 调用直出 JSON）是本产品抽取引擎的最初形态；本 PRD 在产品层面定义其应演进的目标形态，并为后续 V2 架构与原型交付提供需求依据。

### 产品目标

1. **沉淀（Assetize）**：把每场会议稳定转化为高质量结构化数据资产（参会人/要点/待办/决策），可持久化、可检索、可聚合，成为企业的"会议数据底座"。
2. **执行（Actionize）**：让结构化数据自动派生可执行动作——待办自动进任务系统并标注负责人与截止时间，临期/逾期自动跟进提醒责任人，形成闭环。
3. **智能（Intelligize）**：基于沉淀数据做跨会议比对，自动识别任务重复、责任冲突、决策反复，主动提示，避免"会议黑洞"。
4. **可信（Trustworthy）**：每条结论可回链到转写原文，抽取结果经结构化校验，显著降低幻觉与错配，让企业敢用、能落地。
5. **连接（Connect）**：以中台形态标准化对接主流会议生产者与协作消费者，飞书优先、架构中立，可平滑扩展到腾讯会议/Zoom/钉钉等。

### 产品 / 数据现状

当前企业内会议数据的典型现状：转写能力已由各会议软件基本覆盖，但转写之后的结构化处理停留在"人工整理纪要 + 手动建任务"，或依赖通用摘要功能，存在数据孤岛（各平台纪要互不打通）、无统一沉淀（无法跨会议检索比对）、执行断层（纪要与任务系统割裂）三大问题。本产品定位于填补"转写之后、执行之前"的这段空白。

### 用户调研

> 说明：本节为面向作业的假设性调研结论，实际项目应以真实访谈与数据分析报告替换（附录预留位置）。

核心用户画像与痛点（假设性）：

- **项目负责人 / 会议组织者**：最痛"会开完待办落不了地、没人跟进"，希望决策和待办自动进系统并自动催办。
- **参会执行者**：最痛"不知道哪些是我的事、什么时候截止"，希望个人待办自动汇总、临期提醒。
- **管理者 / PMO**：最痛"跨会议信息割裂、任务重复冲突看不见"，希望有跨会议的数据看板与冲突预警。
- **企业 IT / 平台方**：最痛"数据分散、难以私有化沉淀"，希望有统一中台承接并可私有化部署。

关键结论：用户对"摘要好不好看"敏感度在下降，对"待办准不准、能不能自动跟进、会不会漏、会不会冲突"敏感度在上升——这正是本产品的价值锚点。

### 竞品分析

| 竞品 | 定位 | 主要能力 | 关键结论（对本产品而言） |
|---|---|---|---|
| **飞书妙记** | 飞书生态内会议助手 | 转写、章节总结、待办提炼可一键建飞书任务、说话人识别、集成大模型（DeepSeek R1 等）、可视化图表 | 生态内体验强，但为**通用摘要**；企业自定义抽取字段弱、跨会议沉淀与冲突检测缺失、负责人/截止时间无强校验与证据回链。本产品与其**互补**而非正面竞争：定位为可跨生产者、强沉淀与冲突检测的中台层 |
| **Otter** | 可搜索的会议知识库 | 实时协作转写、Channels 归档、说话人识别 | 偏英文、偏检索归档，结构化"决策/待办"抽取不深，执行闭环弱 |
| **Fireflies** | 销售会话智能 | 多语言转写、CRM 字段级自动化、Voice Agent / AI Skills | 面向销售场景与 CRM，通用企业会议与中文场景适配一般 |
| **Granola** | 无 bot 的个人 AI 笔记 | 设备端音频、人工草记 + AI 润色、隐私好 | 依赖人先记，弱结构化、非企业级、无跨会议资产 |
| **通义听悟 / 腾讯会议 AI** | 平台内会议助手 | 中文转写强、待办与摘要提炼 | 同为通用摘要，各自绑定生态，跨平台沉淀与执行闭环缺失 |

**竞品共性与切入口**：转写、通用摘要、说话人识别已是**行业标配（table stakes）**，各家做得都不错。真正未被解决好的是——① 结构化质量与可信度（准确、可校验、可溯源）；② 可执行闭环（待办真正进系统并自动跟进）；③ 跨会议沉淀与冲突检测；④ 跨生产者/消费者的中台连接与私有化。**这四点即本产品的差异化切入口。**

### 功能模块说明

#### 模块一：接入层（Producers Adapter）

- **功能说明**：统一承接来自不同会议生产者的转写文本，屏蔽上游差异，标准化为中台内部的会议输入格式（含转写正文、时间轴、说话人标签、会议元信息）。
- **关键设计**：以适配器模式对接，飞书会议/妙记优先深度打通（回调/开放平台 API），其余生产者以"通用转写文本上传 + API"兜底，保证架构中立、可平滑扩展。
- **输入**：转写文本（可含时间戳、说话人分段）、会议元信息（标题、时间、参会范围，若有）。
- **输出**：标准化会议输入对象，交由抽取引擎处理。

#### 模块二：抽取引擎（V2，核心）

这是作业 Task 03「V2 改进」在产品侧的落点，替代 V1 的"单次 LLM 调用直出 JSON"。

- **场景识别与预处理**：识别会议类型（决策会/评审会/复盘会等），对长文本分段、去除闲聊噪声、处理中英混排与术语缩写，缓解单次调用的注意力稀释与漏抽。
- **说话人与角色归一**：把昵称、花名、"我/咱们"等指代对齐到真实身份与角色，解决参会人与待办负责人错配。
- **分任务抽取**：参会人、讨论要点、待办、决策各用独立子链（子 Agent / 专用 prompt）抽取，避免四类信息在单一 prompt 中互相干扰，可分别优化各自的准确率。
- **结构化校验与重试**：对输出做 Schema 校验（字段完整性、类型、待办必含负责人+截止时间），失败自动重试或降级兜底，杜绝 V1 中 `json.loads` 一崩即全盘失败。
- **证据回链**：每条要点/待办/决策关联到转写原文片段位置，支持一键溯源，作为可信度与人工复核的基础。
- **输出结构（示意）**：

```json
{
  "meeting": { "id": "...", "title": "...", "time": "...", "type": "决策会" },
  "participants": [
    { "name": "张三", "role": "项目负责人", "evidence": "seg_003" }
  ],
  "key_points": [
    { "topic": "上线时间", "summary": "...", "evidence": ["seg_012","seg_015"] }
  ],
  "action_items": [
    { "task": "完成压测报告", "owner": "李四", "due": "2026-07-24",
      "confidence": 0.86, "evidence": "seg_031" }
  ],
  "decisions": [
    { "decision": "采用方案B上线", "status": "final",
      "supersedes": "采用方案A", "evidence": "seg_040" }
  ]
}
```

#### 模块三：沉淀层（Data Asset Store）

- **功能说明**：把抽取结果持久化为跨会议可复用的结构化资产，而非一次性文档。核心实体：会议（Meeting）、人（Person）、待办（Action）、决策（Decision），实体间建立关联（谁负责什么、哪次会决定了什么）。
- **关键能力**：按人/项目/时间/状态检索与聚合；记录决策的时序演变与待办的状态流转（新建→进行→完成/逾期），为看板与冲突检测提供底座。
- **价值**：这是本产品区别于通用摘要工具的根本——**数据可沉淀、可比对、可二次消费**。

#### 模块四：派生与智能层

- **待办派生**：结构化待办自动生成为下游任务，写明负责人、截止时间、来源会议与原文回链。
- **自动跟进提醒**：基于截止时间与任务状态，临期/逾期自动提醒对应责任人（经 IM/邮件），把"催办"自动化。
- **跨会议去重与冲突检测**：新会议产出与历史资产比对，识别：① 重复待办（同一事项多次布置）；② 责任冲突（同一任务指向不同负责人 / 一人负载过重）；③ 决策反复（本次决策与历史决策相悖），主动提示并给出关联证据。
- **说明**：R6/R7 为 P1，MVP 可先实现规则化版本（基于字段与文本相似度），后续升级为语义比对。

#### 模块五：消费 / 集成层（Consumers Integration）

- **功能说明**：把沉淀数据按需分发到下游协作工具，完成"从会议到执行"的闭环。
- **飞书多维表格**（P0）：结构化纪要写入多维表格，天然获得筛选、视图、协作能力，作为消费侧首选落点。
- **飞书任务 / 日历**（P1）：待办建任务、关键节点建日程。
- **IM / 邮件 / Webhook**（P1）：提醒与结果推送、对接企业自有系统。
- **关键设计**：集成层与抽取/沉淀解耦，消费者可插拔，飞书优先、架构中立。

#### 模块六：数据概览看板（Dashboard）

- **功能说明**：中台自身对外提供的可视化总览，让管理者一屏看清会议产出与执行健康度。
- **核心视图**：会议与产出总览（会议数、待办数、决策数）、待办与跟进状态（待办/进行/逾期分布、按人负载）、冲突与风险预警（重复/冲突/决策反复清单）。

## 七、非功能需求

1. **性能**：单场会议（≤1 万字转写）端到端处理时间目标 ≤ 30s；看板与检索查询响应 ≤ 2s。长会通过分段并行降低延迟。
2. **准确性与可信**：待办负责人/截止时间抽取以可评测指标约束（见附录评测方案），关键结论提供证据回链，人工可一键复核与纠正。
3. **可靠性**：抽取失败有重试与降级兜底，保证不因单点解析失败导致整场会议无产出；集成写入具备幂等与重试。
4. **安全与隐私**：会议数据加密存储与传输；多角色权限控制（谁能看哪些会议/待办）；完整操作审计日志；支持私有化部署以满足数据不出企业的要求。
5. **可扩展**：生产者/消费者以适配器插件化接入，新增平台不改动核心；抽取引擎的抽取字段与规则可按会议场景配置。
6. **模型可替换**：抽取引擎与具体模型解耦，支持公有云/私有化模型切换（对应岗位"模型接入"工程要求）。
7. **兼容性**：看板支持主流浏览器（Chrome/Firefox/Edge）与自适应布局。

### B. 需求场景清单（不同会议场景下 V1 的问题）

1. **多人跨部门决策会**：昵称/指代多、角色杂 → 参会人对齐难、待办负责人易错配。
2. **长会 / 半结构化闲聊会（1h+）**：转写超长 → 单次调用注意力稀释、中段漏抽；闲聊被误判为决策。
3. **结论反复变化的会**：先定 A 后改 B → V1 易把作废中间结论当最终决策（需时序理解）。
4. **待办要素不全的会**：口语"你跟进一下"，无 deadline/负责人 → V1 漏抽或幻觉截止时间。
5. **中英混说 / 术语缩写多的会**：专有名词、项目代号识别错 → 要点还原失真。
6. **多话题并行的会**：一会穿插多议题 → V1 输出扁平，要点与待办对不上号。

### C. V1 架构诊断（对应 Task 02）

V1 = 完整转写一次性塞入 prompt、单次 LLM 调用直出 JSON。主要局限：长文本单次调用导致注意力稀释与漏抽；四类信息耦合在同一 prompt 互相干扰；`json.loads` 无兜底，格式一崩整场失败；无说话人/角色对齐；无证据溯源，幻觉不可查；无时序理解，无法处理决策反复；无评测，无法度量与迭代。

### D. 评测方案（对应 Task 05，占位纲要）

- **测试集**：构造带人工标注的会议样本，覆盖附录 B 六类场景。
- **指标**：参会人/角色准确率、要点覆盖率、待办抽取 F1、负责人与截止时间正确率、决策正确率、幻觉率、格式合法率。
- **迭代**：以失败案例驱动 prompt / 子链优化；利用 `human_correction` 埋点数据持续回流改进。
